# API-контракт

Базовый URL: `http://localhost:8000` (в Docker frontend обращается через
`/api` → `backend:8000`). Формат — JSON, `Content-Type: application/json`.

Все ответы об ошибках: `{"detail": "<человекочитаемое сообщение>"}` + HTTP-код.

## Модель доступа к сессиям

При создании сессии (`POST /api/sessions`) backend выдаёт секретный
`token`. Этот токен — единственное доказательство владения диалогом:
знание `session_id` недостаточно. Токен передаётся:

- в теле `POST /api/chat` — поле `session_token`;
- query-параметром `?token=` — `GET /api/sessions/{id}/messages`,
  `DELETE /api/sessions/{id}`;
- в теле `POST /api/leads` — поле `session_token` (обязательно, если
  передан `session_id`).

Без валидного токена операции с сессией возвращают **403**. Токен
возвращается **только** при создании сессии и не выдаётся в
`GET /api/sessions`. Клиент хранит токены локально (localStorage).

Это не полная авторизация — единый пользовательский контур; защита
направлена на то, чтобы чужой `session_id` нельзя было использовать для
чтения истории или присоединения чужого контекста к заявке.

## GET /api/health

Проверка работоспособности backend.

**200 OK**
```json
{
  "status": "ok",
  "ai_mode": "MOCK",
  "ai_status": "mock",
  "version": "0.1.0"
}
```

## POST /api/sessions

Создать новый диалог. История предыдущих сессий сохраняется.

**201 Created**
```json
{
  "id": "9f1c2e4a-...",
  "title": "Новый диалог",
  "created_at": "2026-11-11T12:00:00Z",
  "token": "9c1f..."
}
```

`token` — секрет сессии, сохранить на клиенте. В списке сессий не
возвращается.

## GET /api/sessions

Список сохранённых сессий (новые первыми). Токены не включаются.

**200 OK**
```json
{
  "sessions": [
    {"id": "9f1c2e4a-...", "title": "Новый диалог",
     "created_at": "2026-11-11T12:00:00Z", "message_count": 4}
  ]
}
```

Поле `title` при создании сессии — «Новый диалог». После первого
сообщения пользователя оно автоматически заменяется сокращённым текстом
первого вопроса (до ~60 символов, без LLM) и сохраняется в базе.

## GET /api/sessions/{session_id}/messages?token={token}

История сообщений сессии (по возрастанию времени). Требуется валидный
`token` сессии.

**200 OK**
```json
{
  "session_id": "9f1c2e4a-...",
  "messages": [
    {
      "id": 1,
      "role": "user",
      "content": "У нас несколько магазинов...",
      "sources": null,
      "latency_ms": null,
      "ai_status": null,
      "created_at": "2026-11-11T12:00:01Z"
    },
    {
      "id": 2,
      "role": "assistant",
      "content": "Для такой задачи может подойти облачная платформа учёта...",
      "sources": [{"file": "22-askue.md", "mock": true}],
      "latency_ms": 12,
      "ai_status": "mock",
      "created_at": "2026-11-11T12:00:01Z"
    }
  ]
}
```

`role`: `"user"` | `"assistant"`. У сообщений пользователя `sources`,
`latency_ms`, `ai_status` = `null`.

**404** — сессия не найдена; **403** — отсутствует/неверный `token`.

## POST /api/chat

Отправить сообщение консультанту.

**Запрос**
```json
{
  "session_id": "9f1c2e4a-...",
  "message": "У нас несколько магазинов, хотим контролировать расход электроэнергии.",
  "session_token": "9c1f..."
}
```

| Поле | Тип | Правила |
|---|---|---|
| `session_id` | string (uuid) | обязателен; сессия должна существовать, иначе 404 |
| `message` | string | обязателен; 1–4000 символов после trim |
| `session_token` | string | обязателен для существующей сессии; иначе 403 |

**200 OK**
```json
{
  "session_id": "9f1c2e4a-...",
  "answer": "Для такой задачи может подойти облачная платформа учёта. Сколько у вас объектов?",
  "sources": [
    {"file": "22-askue.md", "mock": true}
  ],
  "latency_ms": 120,
  "suggest_lead": false,
  "ai_status": "mock"
}
```

| Поле | Тип | Описание |
|---|---|---|
| `answer` | string | текст ответа ассистента |
| `sources` | array | источники; в MOCK-режиме помечены `"mock": true` |
| `latency_ms` | integer | реальное время генерации ответа, мс |
| `suggest_lead` | boolean | подсказка фронтенду показать форму заявки |
| `ai_status` | string | `"mock"` \| `"real"` \| `"not_implemented"` |

**Ошибки:** `400` — пустое/слишком длинное сообщение; `404` — нет сессии;
`403` — нет/неверный `session_token`; `422` — невалидный JSON/поля.

В режиме `AI_MODE=REAL` без реализованного AI Core ответ содержит
`ai_status: "not_implemented"` и диагностический текст — это не ошибка HTTP,
а честный статус заглушки.

## DELETE /api/sessions/{session_id}?token={token}

Удалить диалог вместе со всеми его сообщениями (из SQLite, не только из UI).
Требуется валидный `token`.

**204 No Content** — сессия и сообщения удалены.
**404** — сессия не найдена; **403** — отсутствует/неверный `token`.

**Политика хранения:** заявки (`leads`) НЕ удаляются вместе с диалогом.
Их `summary` и `conversation_snapshot` уже сохранены в записи заявки,
поэтому контекст обращения остаётся доступен менеджеру и после удаления
диалога. `session_id` в заявке остаётся исторической ссылкой и может
указывать на удалённую сессию.

## POST /api/leads

Создать заявку менеджеру. Контекст диалога формируется **на сервере** из
SQLite — клиент не может подставить чужую переписку (требуется
`session_token`).

**Запрос**
```json
{
  "name": "Иван Иванов",
  "phone": "+7 900 000-00-00",
  "company": "ООО Ромашка",
  "session_id": "9f1c2e4a-...",
  "session_token": "9c1f..."
}
```

| Поле | Тип | Правила |
|---|---|---|
| `name` | string | 2–200, trim |
| `phone` | string | российский номер; нормализуется к `+7XXXXXXXXXX` (см. ниже) |
| `company` | string | до 200, опционально |
| `session_id` | string \| null | опционален; если задан — сессия должна существовать (404) и нужен валидный `session_token` (403) |
| `session_token` | string \| null | опционален; обязателен при заданном `session_id` |

**Формат телефона.** Backend принимает `9531234567`, `89531234567`,
`79531234567`, `+79531234567`, а также форматированные варианты
(`+7 (953) 123-45-67`). В БД и ответе хранится единый вид
`+79531234567`. Неполные номера и произвольные длинные последовательности
цифр отклоняются (422) — без обрезки «до последних десяти».

**201 Created**
```json
{
  "id": 1,
  "name": "Иван Иванов",
  "phone": "+79000000000",
  "company": "ООО Ромашка",
  "session_id": "9f1c2e4a-...",
  "summary": "У нас несколько магазинов. Можно контролировать их потребление в одном кабинете?\nУточнения клиента: «Объекты в разных городах»",
  "conversation_snapshot": [
    {"role": "user", "content": "У нас несколько магазинов..."},
    {"role": "assistant", "content": "Для такой задачи может подойти..."}
  ],
  "created_at": "2026-11-11T12:05:00Z"
}
```

**Поля контекста:**

- `summary` — детерминированное резюме: первое сообщение клиента как
  основа + последние его сообщения как прямые цитаты-уточнения (лимит
  ~1200 символов). Это **не** ИИ-резюме — только извлечение слов клиента.
  Для пустого диалога — нейтральный текст «детали не уточнены».
- `conversation_snapshot` — JSON-массив `{"role","content"}`: до 50
  последних сообщений, ~8000 символов, без `sources`/`latency_ms`/
  `ai_status` и прочих технических полей. Снимок позволяет позже
  подключить настоящее AI-резюмирование без потери контекста.

**Ошибки:** `404` — `session_id` не существует; `403` — неверный
`session_token`; `422` — нарушения валидации (включая телефон).

## GET /api/leads

Список заявок (новые первыми). **Диагностический endpoint, закрытый по
умолчанию**: возвращает `404`, если не задана переменная окружения
`EXPOSE_LEADS=1` (локальная разработка/тесты). Это защита персональных
данных и истории переписки от публичного доступа — полноценной
авторизации в демо нет, поэтому список не должен быть доступен всем.

**200 OK** (только при `EXPOSE_LEADS=1`)
`{"leads": [Lead, ...]}` — тот же формат элемента, что в POST-ответе.
