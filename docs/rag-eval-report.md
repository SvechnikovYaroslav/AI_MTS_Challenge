## 2. Подтверждённые дефекты (измерено)

**D1. TOP_K=5 обрезает релевантные чанки.**
При дефолтном `TOP_K=5` факт про Магадан (ранг 7) и часть дублей
фактов не попадают в контекст Qwen вообще. Retrieval возвращает top-10,
но в `answer_question` уходит `retrieve(question)` → TOP_K=5.
*Это прямой механизм «важный факт не дошёл до модели».*

**D2. Морфология: точное совпадение токенов без стемминга.**
Токенизатор `[0-9a-zа-яё]+` + `ё→е`, без лемматизации:
- «симки» (запрос) ≠ «сим-картами» (БЗ) — дефис режет слово на
  «сим»+«картами», совпадения нет;
- «оператора» ≠ «операторов», «счётчиках» ≠ «счётчиков».
Измерено на demo id=5: целевой чанк `22-askue#c015` не входит даже
в top-10. Это главный подтверждённый retrieval-промах.

**D3. Диалоги с историей размывают запрос.**
В demo ids 14–18 весь текст диалога (включая реплики ассистента)
становится поисковым запросом: BM25 видит стоп-слова и чужие термины
реплик ассистента наравне с вопросом клиента. Релевантные файлы
обычно находятся (losses→24-losses, price-cat→11-price-categories),
но score «размазан» по лексике всей переписки — риск вытеснения
нужного факта из top-5 выше, чем для одношаговых вопросов.
(Частично смягчается `_retrieval_query` в backend-режиме, но в
конкурсном `solution.py` session_context=None — история идёт
только внутри текста вопроса.)

**D4. Дублирование фактов между продуктовыми документами.**
`26-general.md` повторяет секции ОРЭМ/СЭС/потерь, `21-orem.md` тоже.
В top-10 ids 13, 18 — 5–7 хитов из «Следующий шаг»-секций разных
документов об одном и том же. Это не ошибка, но съедает слоты top-k
и может исказить видимое разнообразие источников для Qwen.

**D5. Микрочанки.** min chunk = 26 символов — шумные короткие
фрагменты получают низкий, но ненулевой score и могут попадать
в tail top-k.

## 3. Недостатки разметки (что нельзя утверждать)

- Нет golden-разметки: неизвестно, какие именно чанки «правильные»
  для каждого из 18 вопросов — таблица `label_template.md` требует
  ручной разметки.
- `demo_output.csv` — демонстрационные ответы организаторов, не эталон.
- Оценка 0,4533 — агрегат скоринга, не разложена по причинам;
  нельзя доказать, что retrieval — причина низких баллов, а не
  генерация/формат ответа.
- P0-пробы — синтетические формулировки, не из реального теста.

## 4. Гипотезы (НЕ подтверждены измерениями)

- Синонимы («объекты»/«площадки», «счётчик»/«прибор учёта») могут
  давать промахи — системно не измерялось.
- Длина запроса: очень длинные диалоги (id 14–18, ~600+ слов) могут
  размывать IDF — не проверено абляцией.
- Отсутствие фильтра по минимальному score: любой score>0 попадает
  в top-k, слабые хвосты могут «шуметь» в контексте.
- 16-regulation.md (1 чанк) и product-map (2 чанка) — возможно,
  документ порезан на слишком крупные куски, детали потеряны
  внутри чанков >1400 симв.

## 5. Приоритетные эксперименты (для следующего этапа)

1. **TOP_K sweep**: 5 → 8/10 на тех же 18 вопросах + P0-пробах;
   замер «факт в контексте» до/после. Дёшево, безопасно.
2. **Ручная разметка** `label_template.md` → посчитать recall@5
   по файлам и по конкретным фактам.
3. **Стемминг/лемматизация** (pymorphy2 или простые префиксные правила)
   — проверить на кейсе «симки/сим-картами» и падежах.
4. **Диалог-aware запрос**: для вопросов с маркерами «Пользователь:»
   извлекать только последнюю реплику + 1–2 ключевых факта клиента.
5. **MMR/дедупликация по файлу или по section** в top-k.
6. **Минимальный score threshold** — отрезать хвосты с score < ε.
7. **Анализ чанка 16-regulation** — укрупнённые секции могли
   потерять структуру.
