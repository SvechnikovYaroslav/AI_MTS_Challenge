# Qwen Generation Audit 1 — аудит пайплайна генерации

Ветка: `feature/qwen-evaluation` (от `develop` @ `fedcd4b`).
Конфигурации: baseline = тег `mts-score-0.4533` (retrieval без
стемминга, TOP_K=5); candidate = `develop` (Retrieval V2, TOP_K=8).
Промпты и параметры модели между вариантами НЕ менялись.
Скрипт сравнения контекстов: `scripts/audit_gen_contexts.py`,
данные: `data/diag/gen_contexts_audit.json` (gitignored).

## 1. Сравнение retrieval-контекстов (78 вопросов)

| Метрика | Baseline (k=5) | V2 (k=8) |
|---|---|---|
| Средний размер user-prompt | 2081 симв. | 3231 симв. (+55%) |
| Вопросов с ≥1 gold-чанком в контексте | 7/78* | 15/78* |
| Demo+P0+E gold coverage (16 размеченных) | 7/16 | 15/16 |

*Подсчёт «gold в контексте» — по всем 78 вопросам (у большинства
разметки нет). Размеченных вопросов ровно **16**
(5 demo + 6 P0 + 5 E-проб); QA49 passage-разметки не имеют.

Ключевые переходы baseline→V2 (gold-чанк появился в контексте):
demo 3 (расширение СЭС), demo 5/p0_sim/e_sim_kol/e_sim_upper/
e_sim_phrase (SIM-семейство), p0_magadan (0/3→3/3 gold-чанков),
p0_ses_expand, p0_units750 (3/4→4/4). Из 16 размеченных: baseline
покрыл gold хотя бы в одном чанке у 7, V2 — у 15; единственный
промах V2: `e_sim_svyaz` — артефакт разметки (вопрос про каналы
связи, не про SIM-карты).

Оценка токенов: +1150 символов ≈ +300–400 входных токенов на вопрос.
При ~150 словах ответа и max_tokens=1200 запас контекста
сохраняется (худший замеренный prompt — ~3.9k симв. ≈ <2k токенов).

Риск TOP_K=8 для генерации: контекст содержит больше «шумовых»
чанков (слабые совпадения по file/section), что может слегка
снизить attention к gold-фрагменту — гипотеза, требует живой модели.

## 2. Аудит HTTP-клиента (`ai_engine._post_chat`)

Что отправляется: `model`, `temperature` (default 0.0), `max_tokens`
(default 1200), `messages` (system+user). Больше ничего.

Что НЕ отправляется и почему это важно для Qwen3.8-27B:

- **`enable_thinking` / `chat_template_kwargs` / `reasoning_effort`** —
  не передаются. По документации Qwen3.8-27B — гибридная thinking-модель,
  thinking **включён по умолчанию** с `reasoning_effort=xhigh`.
  Следствия:
  - рассуждения приходят в `message.reasoning_content` (content
    содержит финальный ответ — наш парсер `content` это переживёт);
  - НО reasoning-токены обычно считаются в лимит completion —
    при `max_tokens=1200` и xhigh-мышлении модель может израсходовать
    бюджет на размышления и вернуть пустой/обрезанный `content`.
    Наш код честно падает с AICoreError на пустой content, но
    **обрезанный по `finish_reason="length"` ответ мы не детектируем** —
    `usage` и `finish_reason` в ответе не читаются вообще.
- **`usage` / `finish_reason` не парсятся** — нет телеметрии расхода
  токенов и детекции truncation. Для аудита качества это слепая зона.
- **Рекомендованные sampling-параметры не совпадают**: для
  thinking-режима Qwen рекомендует temperature=1.0/top_p=0.95,
  для instruct — 0.7/top_p=0.8. Мы шлём temperature=0.0 без top_p —
  допустимо для фактического консультанта, но не валидировано.
- **Retry-политика**: 429/5xx/timeout → до 3 попыток с backoff
  0.5/1.0с — разумно; 400/401 — сразу ошибка (ключ не логируется — OK).
- Пустой/невалидный JSON → AICoreError → честный fallback в
  solution.py — корректно.

## 3. Таблица ошибок и гипотез

| # | Проблема | Статус | Проверка |
|---|---|---|---|
| G1 | Thinking-mode xhigh + max_tokens=1200 → риск пустого/обрезанного content | Гипотеза (сильная, по докам) | Только реальный прокси |
| G2 | finish_reason="length" не детектируется → тихие truncation | Подтверждено кодом | Локально (unit-тест парсинга) |
| G3 | usage не собирается → нет данных о расходе токенов | Подтверждено кодом | Локально |
| G4 | temperature=0.0 вне рекомендованных диапазонов Qwen3.8 | Факт | A/B на прокси |
| G5 | +3 шумовых чанка при TOP_K=8 могут размывать gold | Гипотеза | A/B генерации |
| G6 | KB-QA-046: gold-фрагмент вне top-8 → модель отвечает «нет данных» при наличии факта в БЗ | Подтверждено retrieval | phrase/bigram retrieval |
| G7 | e_sim_svyaz: неверная gold-разметка, не дефект | Подтверждено | — |
| G8 | `_retrieval_query` для follow-up добавляет только последнее user-сообщение — может терять уточняющие параметры из более ранних реплик | Гипотеза | Диалоговые тесты |

## 4. Что проверено локально / что требует модели

Локально (уже есть): retrieval-метрики обеих конфигураций,
размеры контекстов, unit-тесты HTTP-клиента (mock-сервер: 200/400/
401/429/500/timeout/invalid JSON — все ветки).

Требует реального прокси МТС: фактическое качество ответов,
влияние thinking-режима на max_tokens, расход токенов, таймауты
на xhigh-мышлении (60с может не хватать!).

## 5. Рекомендации до следующего сабмита (по приоритету)

1. **Диагностический сабмит**: добавить в `solution.py` лог
   `finish_reason`/`usage` (если прокси возвращает) — минимальное
   изменение, даёт данные о truncation. Либо разовый probe-скрипт.
2. Если thinking съедает бюджет — рассмотреть
   `chat_template_kwargs.enable_thinking=false` или
   `reasoning_effort=low` (через extra payload-поле; совместимость
   с прокси МТС неизвестна — проверить).
3. Поднять `MAX_TOKENS` до ~2000+ или уменьшить — зависит от
   замеров usage на прокси.
4. A/B: TOP_K=5 vs 8 на одних вопросах с реальной моделью —
   единственный способ проверить гипотезу G5.
5. Не менять промпты до замеров — текущий промпт уже содержит
   все ключевые ограничения (не выдумывать, уточняющий вопрос,
   честный отказ).

## 6. Ограничения этого аудита

- Реальный Qwen-прокси недоступен локально (нет .env/ключей) —
  качество ответов НЕ оценивалось; mock не подменял оценку.
- Точный billing/лимиты прокси МТС неизвестны.
- Имена моделей/параметров взяты из публичной документации
  Qwen3.8-27B (HF/QwenCloud/NVIDIA NIM/Groq) — прокси организаторов
  может отличаться.
